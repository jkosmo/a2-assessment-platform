# Designnotat: repetisjonsmodus for flervalg (#1061, #1062)

Skrevet før endringen, etter regel 1 i `CHANGE_DESIGN_RULES.md`. To saker fra produkteier 16.09
som hører sammen: noen flervalgsmoduler skal **understøtte læring**, ikke måle. Da vil man ha en
bank med mange spørsmål, et tilfeldig utvalg i tilfeldig rekkefølge per forsøk (#1062), og en
gjennomgang etterpå av det som ble feil — med riktig svar og begrunnelse (#1061).

## Slik er det i dag (målt i koden, ikke antatt)

| | Hvor | Hva |
|---|---|---|
| Spørsmålene | `MCQSetVersion` → `MCQQuestion` (`stem`, `optionsJson`, `correctAnswer`, `rationale?`, `active`) | Én liste per versjon. `rationale` finnes alt og genereres med spørsmålene. |
| Forsøket | `MCQAttempt` (per `Submission`), `MCQResponse` (én per spørsmål, `@@unique`) | Forsøket vet **ikke** hvilke spørsmål som ble stilt — det er «alle aktive i settet». |
| Utlevering | `startMcqAttempt` (`mcqService.ts`): `findActiveQuestionsForSet` → **alle**, i `createdAt asc` | **Alternativene stokkes alt** (`shuffleArray(options)`) — per kall, så en ny lasting gir ny rekkefølge på alternativene. Spørsmålene stokkes ikke. |
| Retting | `submitMcqAttempt`: `totalQuestions = questions.length` (alle aktive), `percentScore`, `passFailMcq` mot `resolveMcqMinPercent(policy)` | Svar på spørsmål som ikke er i settet ignoreres. |
| Deltakerens resultat | `submissionReadModels.ts`: `mcqScaledScore`, `mcqPercentScore`, `mcqMinPercent` | Prosent og bestått. Ingen fasit, ingen begrunnelse — riktig for prøver (#903 tettet nettopp en fasitlekkasje). |
| Nytt forsøk | `submissionService.ts`: ny `Submission`, forrige `SUPERSEDED` (#951: forlatt forsøk er ikke et utfall) | Finnes. Ny `Submission` → ny `MCQAttempt`. |
| Policy per modul | `assessmentPolicyJson` på `ModuleVersion` (`assessmentPolicyCodec`, `assessmentPolicyBodySchema`) | `scoring`, `passRules` (`mcqMinPercent` …), `aiInfluence`. Redigeres under Innstillinger. |
| Generering | `generateMcqInBackground` → `sessionDraft.mcqQuestions = …` | **Erstatter** utkastets spørsmål. Maks 20 per kjøring (`questionCount`). |
| Import | `contentImportService.ts` | Pakken bærer hele settet; ny `MCQSetVersion`. |

To ting saken ikke visste: alternativene stokkes allerede (halve #1032-bekymringen er borte), og
retten «hvilke spørsmål fikk deltakeren» finnes ikke som data — det er den ene tingen alt annet
henger på.

## Beslutninger

### 1. Én innstilling styrer hele modusen — ikke tre brytere

`assessmentPolicy.mcq` får tre felt, redigert under Innstillinger:

```ts
mcq?: {
  questionsPerAttempt?: number;   // tomt = alle (dagens oppførsel)
  shuffleQuestions?: boolean;     // standard TRUE — også for moduler som finnes (produkteier 17.09)
  reviewAfterSubmit?: boolean;    // #1061: vis feil svar med riktig svar og begrunnelse
}
```

Hvorfor tre felt og ikke én «repetisjonsmodus»-bryter: en prøve kan godt ha stokket rekkefølge uten
gjennomgang, og en repetisjon kan vise alle spørsmål. Men UI-et **presenterer** dem samlet under
overskriften «Flervalg» med en forklaringslinje per felt, så SMO ser sammenhengen. Standarder:
`questionsPerAttempt` tomt = alle (i dag), `reviewAfterSubmit` av (fasit er en egen dør), men
**`shuffleQuestions` på** — produkteier 17.09: rekkefølgen stokkes for alle flervalgsmoduler fra
neste deploy, også de som finnes, uten at noen må velge det. SMO kan slå det av per modul.

Policyen er riktig sted (ikke `MCQSetVersion`): dette er regler for *hvordan settet brukes*, ikke
innhold, og de følger modulversjonen som `mcqMinPercent` gjør. Gaten og eksport/import bærer
policyen alt.

### 2. Forsøket husker trekket — som data, ikke som utregning

`MCQAttempt` får `questionOrderJson: String?` — en ordnet liste av `questionId` slik de ble stilt.

- `startMcqAttempt`: når forsøket **opprettes**, trekkes `questionsPerAttempt` tilfeldig fra de
  aktive spørsmålene (alle hvis tomt), stokkes hvis `shuffleQuestions`, og lagres. Åpnes forsøket
  igjen (ny lasting midt i), leses lista — samme spørsmål, samme rekkefølge.
- `submitMcqAttempt`: retter mot **de stilte** (`questionOrderJson`), ikke alle aktive.
  `totalQuestions` = antall stilte. Svar på spørsmål utenfor trekket ignoreres som i dag.
- Eldre forsøk uten `questionOrderJson` behandles som «alle aktive, lagret rekkefølge» — ingen
  migrering av data, bare ny kolonne (nullable).

Hvorfor lagre og ikke regne ut fra et frø: gjennomgangen (#1061), rapportene og et eventuelt
klagemål må kunne si nøyaktig hva deltakeren fikk, også etter at banken er fylt på med en ny
`MCQSetVersion`. Forsøket peker alt på sin `mcqSetVersionId`; lista gjør resten eksplisitt.

### 3. Gjennomgangen er et eget lesekall, styrt av policyen på tjeneren

`GET /api/participant/modules/:moduleId/submissions/:submissionId/mcq-review` (deltakerens egen):

```ts
{ enabled: boolean, questions: Array<{ id, stem, options, selectedAnswer, correctAnswer, isCorrect, rationale }> }
```

- Tjeneren svarer `enabled: false` og **tom liste** når `reviewAfterSubmit` ikke er satt for den
  modulversjonen forsøket ble tatt på. Fasit går aldri ut i noe annet deltakerkall — heller ikke i
  det eksisterende resultatet. Det er den samme regelen som #903: fasit er en egen dør.
- Rekkefølgen er `questionOrderJson`. Alle stilte spørsmål er med (`isCorrect` skiller), så
  visningen kan velge å vise bare feil, eller alt — det avgjøres i klienten uten nytt kall.
- Språk: `stem`, `options`, `correctAnswer`, `rationale` lokaliseres med samme hjelpere som
  utleveringen (`localizeContentText`/`Array`), i deltakerens språk. `rationale` er alt med i
  publiseringsgaten (`validateMcqTranslationCompleteness` sjekker stem, alternativer, riktig svar
  og begrunnelse), så en publisert modul har begrunnelsen på alle tre språk.
- Vises **også når deltakeren består** (læring er poenget), og på Fullførte-sida (samme kall, samme
  policy) — ikke bare rett etter innlevering.

### 4. Påfylling er additiv i alle tre veiene

- **Generering** («Generer spørsmål»): dialogen viser «Banken har N spørsmål» og spør «Hvor mange
  nye?». Resultatet **legges til** `sessionDraft.mcqQuestions` i stedet for å erstatte. De
  eksisterende stammene sendes med i genereringskallet som «ikke gjenta disse» — ellers blir 30
  spørsmål 30 varianter av de samme 10. Grensen på 20 per kjøring består; flere kjøringer fyller på.
- **Manuelt**: «Legg til spørsmål» i Rediger finnes. Banken kan bli lang → hvert spørsmål som
  sammenfoldet rad med stammen som overskrift (samme `.form-row` som ellers), utfoldet ved klikk.
- **Import fra skillet**: `contentImportService` legger nye spørsmål til eksisterende sett (ny
  `MCQSetVersion` = gamle + nye). Eksplisitt `replace: true` i pakken erstatter. Skillets
  `package-schema.md` sier det.

Lagring er som i dag: ny `MCQSetVersion` med hele banken. Pågående forsøk beholder trekket sitt fra
versjonen de startet på (beslutning 2).

### 5. Utenfor denne leveransen

- Prioritering av spørsmål deltakeren har svart feil på før (adaptiv repetisjon). Krever historikk
  på tvers av forsøk; kommer naturlig etter at trekket er data.
- Tidsgrense per forsøk, maks antall forsøk. Egen sak om noen ber om det.
- Stokking av alternativene: finnes alt. #1032 (rett svar røper seg ved lengde/plassering) er et
  genereringsproblem i skillet, ikke et utleveringsproblem.

## Berøringspunkter

| Lag | Endring |
|---|---|
| Prisma | `MCQAttempt.questionOrderJson String?` — én migrasjon, ingen dataflytting |
| Codec/schema | `assessmentPolicyCodec` + `assessmentPolicyBodySchema`: `mcq` med tre felt |
| `mcqService.ts` | trekk + stokking ved opprettelse; retting mot de stilte; ny `getMcqReview` |
| `routes/participant*` | `GET …/mcq-review`; ingen endring i eksisterende resultat |
| Innstillinger-fanen (`admin-content-settings-tab.js`) | gruppe «Flervalg»: antall per forsøk, stokk rekkefølge, vis gjennomgang — lagres med policyen |
| «Generer spørsmål»-dialogen / `generateMcqInBackground` | «Banken har N», antall nye, additiv, «ikke gjenta» |
| `contentImportService.ts` + skillets `package-schema.md` | additiv import, `replace` |
| `participant.js` | gjennomgang etter innlevering og på Fullførte |
| Rapporter | «andel riktig per spørsmål» får ulikt antall svar per spørsmål — teller vises |
| Tester | enhet: trekk/stokking/retting; integrasjon: forsøk husker trekket, review 403/tom uten policy; e2e: Innstillinger, dialog, deltakerens gjennomgang |

## Rekkefølge (fire leveranser, hver grønn for seg)

1. **Trekket som data**: migrasjon, policyfeltene, `startMcqAttempt`/`submitMcqAttempt`,
   Innstillinger-feltene «per forsøk» og «stokk». Synlig for deltakeren: færre og stokkede spørsmål.
2. **Gjennomgangen** (#1061): review-kallet og deltakervisningen (etter innlevering og på Fullførte).
3. **Additiv påfylling**: generering med «ikke gjenta», sammenfoldede rader i Rediger, additiv
   import i skillet.
4. **Rapportene**: teller per spørsmål.

## Avklart med produkteier 17.09

- Gjennomgangen gjelder også **fritekst + flervalg** (flervalgsdelen) — ikke bare rene flervalgsmoduler.
- Nytt forsøk på en repetisjonsmodul gir **nytt trekk**.
- `shuffleQuestions` er **på som standard**, også for eksisterende moduler.
